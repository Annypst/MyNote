## 📋 1. 请求转发（Forward）与重定向（Redirect）的本质区别？

这是 Java Web 简答题里当之无愧的“定海神针”，作答时必须从以下四个维度进行像素级切分：

- **触发机制与流转管道**：

  - 

    **转发**：是服务器内部的“暗箱操作” 。Servlet 调用 `request.getRequestDispatcher().forward(request, response)` 将请求接力给下一个资源，整个过程只发生 **1 次请求和 1 次响应** 。  

  - 

    **重定向**：是服务器与浏览器的“双向指挥” 。服务器向浏览器下发 `302` 状态码和 `Location` 响应头，逼迫浏览器重新发起向新地址的请求，整个过程共发生 **2 次请求和 2 次响应** 。  

- **浏览器地址栏表现**：

  - 

    **转发**：由于是服务器内部跳转，**浏览器地址栏的 URL 绝对不会发生任何改变** 。  

  - 

    **重定向**：由于浏览器重新发起了全新的请求，**地址栏会瞬间变为新资源的完整 URL** 。  

- **Request 域口袋数据生存期**：

  - 

    **转发**：由于自始至终处于同一个请求管道中，因此存储在 Request 域口袋中的属性（Attribute）对象**可以安全地带给下一个页面共享** 。  

  - **重定向**：由于前一次请求在服务器下发 302 时就已经宣告终结，第二次请求是一个全新的口袋，因此**之前 Request 域口袋里的数据会彻底丢失**。

- **路径访问权限边界**：

  - **转发**：死死死死局限在**当前 Web 应用的内部**，绝对无法访问外部网站（如百度）。
  - **重定向**：无拘无束，既可以跳转到本项目的其他页面，也可以**直接飞往任何外部站点的绝对 URL**。

## 📋 2. 会话跟踪技术中，Cookie 与 Session 的核心对比？

作答时要牢记“一个在客户端流浪，一个在服务器坐镇”的本质 ：  

| **对比维度**     | **🍪 Cookie 技术**                                            | **🔑 Session 技术**                                           |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **存储物理位置** | 寄生在**客户端浏览器**中（内存或本地硬盘） 。                | 牢牢端坐在**服务器端内存**中 。                              |
| **数据安全性**   | 极其不安全。由于在客户端以明文/纯文本流转，极易被篡改或拦截。 | 安全性极高 。关键数据保存在服务器，客户端无法触及 。         |
| **存储数据类型** | 死死只能存储 **`String` 字符串**。                           | 全能打手。可以存储**任意类型的 Java 对象（Object）** 。      |
| **数据大小上限** | 单个 Cookie 大小被限制在 **4KB** 左右，数量也受浏览器限制 。 | 理论上**完全没有大小上限**，纯粹取决于服务器内存的硬件厚度。 |
| **二者血缘机制** | 属于独立的个体。                                             | **Session 默认必须强制基于 Cookie 运作** 。服务器通过下发名为 `JSESSIONID` 的 Cookie 与客户端对暗号来对齐会话 。 |

## 📋 3. 详细阐述 Servlet 的生命周期及其三大核心阶段？

这是考核“组件从生到死”生命轨迹的学术必考点：

- **初始化阶段（装载与出生）**：

  - 当 Servlet 首次被请求访问时（或配置了 `<load-on-startup>` 启动加载） ，Tomcat 负责将其 class 文件加载进内存并实例化 。  
  - 紧接着，Tomcat 会强行调用且**仅仅调用 1 次 `init(ServletConfig config)` 方法** 。这个方法是 Servlet 生命的起点，用于初始化全局资源 。  

- **服务阶段（并发承载）**：

  - 每次有浏览器请求打中该 Servlet 的虚拟路由时，Tomcat 都会开启一个新线程，**多次、反复地调用它的 `service(request, response)` 方法** 。  

  - 

    `service` 方法会根据当前 HTTP 请求的 Method 动作类型（GET/POST），自动将请求分发路由给对应的 `doGet()` 或 `doPost()` 方法进行具体的业务处理 。  

- **销毁阶段（寿终正寝）**：

  - 当 Web 应用被卸载、或者 Tomcat 服务器正常关闭那一瞬间，Tomcat 会强制调用且**仅仅调用 1 次 `destroy()` 方法** 。  
  - 该方法执行完毕后，Servlet 实例沦为垃圾，等待 JVM 内存回收 。  

## 📋 4. HTTP 协议中，GET 请求方式与 POST 请求方式的底层本质区别？

如果考到这道题，如果只答“一个安全，一个不安全”，在严谨的专业改卷中拿不到满分。必须写出以下底层血缘差异：

- **参数承载位置与隐蔽性**：

  - **GET**：将请求参数直接以 `?name=value&age=18` 的明文键值对形式，**强行追加在 URL 后面**。由于暴露在地址栏，极不安全。

  - 

    **POST**：把参数和数据死死包裹在 HTTP 报文的实体内容（Entity Body）内部，地址栏一片清爽，隐蔽性极强 。  

- **传输数据量天花板限制**：

  - 

    **GET**：由于参数挂在 URL 屁股后面，而浏览器和服务器对 URL 的全长具有严格的物理空间限制，因此传输数据一般**不能超过 2KB ~ 8KB** 。  

  - 

    **POST**：数据寄生在请求体中，**在理论上是完全没有体积上限限制的**（常用于大文件、视频断点续传） 。  

- **幂等性与浏览器缓存机制**：

  - 

    **GET**：学术上属于“幂等操作”，通常只用于查询数据（不改变服务器状态） 。浏览器会主动、贪婪地对 GET 请求的页面和参数进行**历史记录与快取缓存**。  

  - 

    **POST**：非幂等操作，用于增删改写数据（会改变服务器状态） 。浏览器**绝对不会自动缓存 POST 请求**，每次刷新页面都会弹窗警告用户“是否重新提交表单”。  

## 📋 5. 详细描绘 JSP Model2 架构模型中 MVC 各自扮演的角色与协作流程？

这是系统工程大题的理论地基，必须将三个英文字母在 Java Web 里的具体肉身解释得淋漓尽致 ：  

- 

  **C（Controller 控制器） ➡️ 严格由 `Servlet` 承担** ：  

  - 它是全站的第一道物理防线。负责被动接收浏览器的 HTTP 请求 ，从中掏出请求参数 ，并具备生杀大权，负责调度和指挥底层的业务 Model 。  

- 

  **M（Model 模型） ➡️ 严格由 `JavaBean / DAO` 承担** ：  

  - 它是纯粹的数据和规则大本营 。负责封装具体的业务属性，手工连接数据库（JDBC）执行具体的 SQL 增删改查 ，将冷冰冰的逻辑转化成温暖的 Java 对象数据 。  

- 

  **V（View 视图） ➡️ 严格由 `JSP / HTML` 承担** ：  

  - 它不掺杂任何复杂的业务逻辑。专门负责从作用域口袋里取出 Controller 塞给它的展示数据 ，利用 JSTL/EL 表达式将其转化为绚丽的 HTML 结构，最终渲染给用户看 。  

## 📋 6. JDBC 原生底层操作中，Statement 与 PreparedStatement 的核心区别？

面对高频的数据库访问大盘，简答题往往喜欢抠这两个接口的编译时差 ：  

- **预编译与执行时差**：

  - 

    **`Statement`**：是一个普通的、没有提前编排的执行器 。每次执行 `stat.executeQuery(sql)` 时，都会把整条 SQL 现巴巴地发给 MySQL，进行**现编译、现执行**，效率低下 。  

  - 

    **`PreparedStatement`**：是预编译接口 。在 Connection 创建它的一瞬间（`con.prepareStatement(sql)`），就已经把带有 `?` 占位符的 SQL 命令发送给 MySQL **提前进行了语法树编译与解析** 。后期多次调用只需传入参数，直接秒级执行 。  

- **防止 SQL 注入漏洞的天职**：

  - **`Statement`**：由于采取字符串直接拼接的方式构造 SQL，黑客可以通过输入 `' or '1'='1` 的恶毒参数，轻易非法攻破登录校验，产生严重的 **SQL 注入漏洞**。

  - 

    **`PreparedStatement`**：采用参数化占位符 `?` 机制 。黑客输入的任何恶意特殊字符，在执行时都会被底层强行当作“最普通的纯文本字面量”进行转义，**在学术上天然、彻底地杜绝了 SQL 注入攻击** 。
