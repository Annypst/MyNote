## 进程同步和互斥

**进程互斥**与**进程同步**是操作系统处理多进程并发执行时的两类基本制约关系。用最本质的话概括：

- **互斥（Mutual Exclusion）**：本质是“竞争独占资源”**，解决的是**“谁能用”的问题（你用的时候我不能用）。
- **同步（Synchronization）**：本质是“协作配合次序”**，解决的是**“谁先谁后”的问题（你做完某步我才能开始）。

### 1. 进程互斥（间接相互制约关系）

#### 概念与本质

当多个并发进程需要访问**同一临界资源（Critical Resource）**（即物理上或逻辑上一次只允许一个进程使用的独占资源，如打印机、声卡、共享内存中的计数器）时，任何时刻**只允许一个进程**进入对应的临界区（Critical Section）执行，其他进程必须在外面等待。

因为各进程本身并不知道对方的存在，它们只是都在向操作系统申请同一块资源，所以学术上称为“间接相互制约关系”。

#### 互斥机制必须满足的准则

为了安全且高效地实现互斥，操作系统设计了四个基本原则：

1. **空闲让进**：临界区空闲时，应允许一个请求进入的进程立即进入。
2. **忙则等待**：已有进程处于临界区时，其他试图进入的进程必须等待。
3. **有限等待**：等待进入临界区的进程必须在有限时间内能够进入，防止饥饿。
4. **让权等待**：当进程不能进入临界区时，应立即释放 CPU（如记录型信号量的 `block` 操作），避免陷入死循环忙等。

#### 经典例子

- **生活场景**：单人更衣室。门开着谁都能进；只要里面有人锁上门，外面的人不论是谁都必须在门外等待，直到里面的人出来。
- **代码特征**：P 操作与 V 操作紧紧包围临界区，成对出现在**同一个进程**内。

### 2. 进程同步（直接相互制约关系）

#### 概念与本质

某些并发进程在逻辑上是**相互协作**的伙伴关系。为了共同完成一项复杂的系统任务，它们的推进步调必须严格遵循某种**先后依赖关系（前趋关系）**。

进程 A 运行到某个检查点时，必须等待进程 B 发出“某项前置工作已完成”的信号；在没有收到该信号前，进程 A 必须暂停推进。因为两个进程在逻辑上存在直接的数据交互或依赖，所以学术上称为“直接相互制约关系”。

#### 经典例子

- **生活场景**：工厂流水线。工人 B 负责“给包装盒贴标签”，工人 A 负责“把产品装进包装盒”。工人 B 必须等工人 A 组装并推过来一个盒子后才能贴，不能先贴不存在的盒子。
- **系统场景**：生产者-消费者问题中，消费者不能从“空缓冲区”中取数据，必须等生产者先写入并通知；音频播放器不能直接解码音频帧，必须等网络接收线程先将数据包下载到缓冲区中。
- **代码特征**：P 操作（等待/测试）和 V 操作（通知/释放）分别放在**两个不同的进程**中。

### 3. 两者的核心区别对比

| **比较维度**   | **进程互斥**                             | **进程同步**                                 |
| -------------- | ---------------------------------------- | -------------------------------------------- |
| **制约关系**   | **间接**相互制约（通过共享资源产生关联） | **直接**相互制约（存在直接的协作与依赖关系） |
| **关注核心**   | 资源的**独占性**与安全访问               | 事件执行的**先后时序**（前趋图）             |
| **进程感知**   | 互不关心对方是谁，只竞争资源             | 明确知晓协作流程，必须等待对方的信号         |
| **PV 布局**    | P 和 V 成对出现在**同一进程**内部        | P 在等待进程中，V 在前置进程中（**跨进程**） |
| **信号量初值** | 通常设为 **1**（表示 1 份可用临界资源）  | 通常设为 **0**（表示前置事件尚未完成）       |



## PV操作

PV 操作（来源于荷兰语 *Proberen* 意为测试/申请，*Verhogen* 意为增加/释放）本质上是一对必须保证原子性（不可被中断）的系统原语，其核心是对一个表示**可用资源数量**的信号量 $S$ 进行增减和进程调度。

以操作系统中最经典的**记录型信号量**为例，可以从数据结构、执行逻辑以及实际应用三个层面来理解：

### 1. 数据结构与物理含义

记录型信号量由一个整型变量和一个进程等待队列组成：

C

```
typedef struct {
    int value;               // 资源计数
    struct process_node *L;  // 等待该资源的进程阻塞队列
} semaphore;
```

变量 $S.value$ 的数值具有明确的物理意义：

- **$S.value > 0$**：表示系统中当前还有多少个**空闲可用**的该类资源。
- **$S.value = 0$**：表示该类资源刚好被分配完毕，且**没有**进程在等待排队。
- **$S.value < 0$**：表示资源已被耗尽，且其绝对值 $\vert{}S.value\vert{}$ 严格等于**当前在该信号量队列中被阻塞挂起的进程数量**。

### 2. P 操作与 V 操作的执行逻辑

#### P 操作：申请资源（又称 wait 操作）

C

```
void wait(semaphore S) {
    S.value--;
    if (S.value < 0) {
        // 资源不足，将当前进程挂入等待队列，转为阻塞态
        block(S.L);
    }
}
```

- **逻辑拆解**：
  1. 只要来申请，计数器先减 1（`S.value--`），表示“我预定或占用了一个”。
  2. 减完之后判断：如果结果小于 0（说明在减之前，资源就已经 $\le 0$ 了），系统无法满足当前请求，当前进程必须调用 `block` 自行阻塞，让出 CPU，进入等待队列。

#### V 操作：释放资源（又称 signal 操作）

C

```
void signal(semaphore S) {
    S.value++;
    if (S.value <= 0) {
        // 还有进程在排队，从等待队列中唤醒一个进程
        wakeup(S.L);
    }
}
```

- **逻辑拆解**：
  1. 进程归还资源，计数器加 1（`S.value++`）。
  2. 加完之后判断：如果结果仍然 $\le 0$（说明在加 1 之前，负数绝对值至少是 1，队列中至少有一个进程在挂起等待），此时系统必须调用 `wakeup` 从等待队列中唤醒一个被阻塞的进程，让其进入就绪态。

### 3. PV 操作解决“互斥”与“同步”的区别

很多时候理解困难，是因为混淆了 PV 是用于**互斥**还是**同步**：

#### 互斥模式（保护临界资源）

- **初值**：通常设为 $1$（表示临界资源仅有 1 份可用）。
- **使用方式**：P 操作与 V 操作成对出现在**同一个进程**中，紧紧包裹住临界区。

C

```
P(mutex);
// 临界区代码（访问共享资源）
V(mutex);
```

#### 同步模式（控制先后执行顺序）

- **初值**：通常设为 $0$（表示前置事件未完成时，该条件不可用）。
- **使用方式**：P 操作与 V 操作分别出现在**不同的两个进程**中，V 充当“通知”，P 充当“等待”。

C

```
// 进程 A（先执行）：
A 的操作;
V(S); // 完成后发出信号，给 S 增加 1

// 进程 B（后执行）：
P(S); // 检查信号，如果 A 还没执行完，S 仍为 0，减 1 后为 -1，B 阻塞等待；若 A 已完成，S 为 1，减 1 后为 0，B 继续执行
B 的操作;
```

## 区别

这四种信号量的演进，本质上是为了解决两个核心矛盾：**CPU 是否忙等（是否满足“让权等待”）** 以及 **多资源申请时的死锁与分配效率**。

### 1. 整型信号量（Integer Semaphore）

- **定义与数据结构**：仅包含一个用于表示资源数目的整型变量 $S$。

- **操作逻辑**：

  C

  ```
  void wait(int S) {
      while (S <= 0); // 资源不足时死循环检测
      S--;
  }
  void signal(int S) {
      S++;
  }
  ```

- **核心缺陷**：**违背“让权等待”原则**。当资源不足时，进程在 `wait` 中陷入 `while` 死循环，持续占用 CPU 进行“忙等”（Busy Waiting），造成计算资源的极大浪费。

### 2. 记录型信号量（Record-Type Semaphore）

- **演进动机**：消除忙等，让拿不到资源的进程主动让出 CPU。

- **定义与数据结构**：包含资源计数值 `value` 和进程阻塞链表指针 `L`。

  C

  ```
  typedef struct {
      int value;
      struct process_node *L;
  } semaphore;
  ```

- **操作逻辑**：

  - **P(S)**：`S.value--`；若 `S.value < 0`，调用 `block()` 自行挂起，放入队列 $S.L$。
  - **V(S)**：`S.value++`；若 `S.value <= 0`，调用 `wakeup()` 从队列 $S.L$ 唤醒一个进程。

- **优势**：严格满足“让权等待”，CPU 利用率大幅提高。

- **局限**：一次 PV 只能申请/释放一种资源的 1 个单位。如果一个进程需要同时获取多种不同的临界资源（如哲学家就餐问题），按顺序分别执行多次 P 操作极易引发**死锁（Deadlock）**（各持有一部分，互相等待对方释放）。

### 3. AND 型信号量（AND Semaphore）

- **演进动机**：解决多类资源同时申请时的死锁问题（破坏死锁的“占有并等待/请求与保持”条件）。

- **核心机制**：**全部分配，或者一个都不分配（All-or-Nothing）**。将进程在整个运行过程中所需要的全部共享资源，在申请时以原子操作的形式一次性全部下发；只要有任何一个资源不能满足，就一个也不分配，进程进入等待。

- **操作接口**：$Swait(S_1, S_2, \dots, S_n)$ 与 $Ssignal(S_1, S_2, \dots, S_n)$。

- **操作逻辑**：

  C

  ```
  void Swait(S1, S2, ..., Sn) {
      if (S1 >= 1 && S2 >= 1 && ... && Sn >= 1) {
          for (int i = 1; i <= n; i++) S_i--;
      } else {
          // 将当前进程挂入第一个资源不足的 S_k 的等待队列中（或专用等待队列）
          block();
      }
  }
  void Ssignal(S1, S2, ..., Sn) {
      for (int i = 1; i <= n; i++) {
          S_i++;
          // 将等待在 S_i 队列上的进程唤醒并转移到就绪队列
      }
  }
  ```

- **局限**：每次申请和释放的单位固定为 1，无法灵活应对“单次需要 $d$ 个资源”或“资源低于安全阈值不予分配”的需求。

### 4. 信号量集（General Semaphore Set）

- **演进动机**：在 AND 型信号量的基础上，进一步支持**批量申请**与**阈值控制**。
- **操作参数**：
  - 申请：$Swait(S_1, t_1, d_1; \; S_2, t_2, d_2; \; \dots; \; S_n, t_n, d_n)$
  - 释放：$Ssignal(S_1, d_1; \; S_2, d_2; \; \dots; \; S_n, d_n)$
  - 其中：
    - $S_i$：当前可用资源数。
    - $t_i$：**测试阈值（Threshold）**，要求当前资源 $S_i \ge t_i$ 时才允许分配（作为警戒线/防死锁下限）。
    - $d_i$：**实际需求量（Demand）**，满足分配条件后，扣减的资源数 $S_i = S_i - d_i$（要求 $t_i \ge d_i$）。
- **特殊退化情形**：
  - 当所有 $t_i = 1, d_i = 1$ 时，信号量集退化为 **AND 型信号量**。
  - 当仅有 1 个信号量且 $t = 1, d = 1$ 时，信号量集退化为**记录型信号量**（互斥模式）。
  - 若 $d = 0$（例如 $Swait(S, t, 0)$），则只判断资源是否达到下限 $t$，不实际消耗资源，相当于一个可控的**条件门禁/同步开关**。

### 四者综合对比

| **信号量类型** | **核心数据结构 / 参数**          | **是否忙等**           | **资源分配粒度**                     | **防死锁能力**           |
| -------------- | -------------------------------- | ---------------------- | ------------------------------------ | ------------------------ |
| **整型**       | 单个 `int S`                     | **是**（违背让权等待） | 1 种资源，每次 1 个                  | 弱（容易死锁）           |
| **记录型**     | `int value` + 阻塞队列 `L`       | **否**（让权等待）     | 1 种资源，每次 1 个                  | 弱（多资源嵌套易死锁）   |
| **AND 型**     | 集合 $\{S_1, S_2, \dots, S_n\}$  | **否**                 | 多种资源，每次各 1 个（原子分配）    | **强**（破坏请求与保持） |
| **信号量集**   | 三元组集合 $\{(S_i, t_i, d_i)\}$ | **否**                 | 多种资源，单次需求 $d_i$，阈值 $t_i$ | **强**（高度灵活与可控） |

## 哲学家就餐问题

**哲学家就餐问题（Dining Philosophers Problem）\**是由计算机科学家 Edsger Dijkstra 于 1965 年提出的一个经典的\**多进程竞争共享资源、进程同步与死锁**模型。

它通过一个生动的生活场景，抽象了操作系统中多个进程同时请求多个互斥资源时的典型矛盾。

### 1. 问题模型设定

- **场景**：5 位哲学家围坐在一张圆桌旁，他们的生活极其简单，只在思考（Thinking）**和**就餐（Eating）两种状态之间切换。
- **资源配置**：圆桌上有 5 只碗和 **5 根筷子**（每两位哲学家之间只放了一根筷子）。
- **行为规则**：
  - 哲学家饥饿时，必须**同时拿到左右两边的两根筷子**才能开始进餐。
  - 进餐完毕后，放下两根筷子并继续思考。
  - 筷子是互斥的，同一根筷子同一时刻只能被一人使用，且不能强行从别人手中抢夺。

### 2. 映射到操作系统的本质

| **现实模型元素**   | **操作系统中的物理本质**                                     |
| ------------------ | ------------------------------------------------------------ |
| **哲学家**         | 并发执行的**进程 / 线程**                                    |
| **筷子**           | 必须互斥访问的**临界资源**（通常用互斥信号量表示，初值为 1） |
| **同时拿两根筷子** | 进程在推进过程中需要**同时持有多种不同的共享资源**           |
| **就餐过程**       | 进入**临界区（Critical Section）**执行任务                   |

### 3. 朴素方案与死锁的发生

如果为每根筷子设置一个记录型信号量 `semaphore chopstick[5] = {1, 1, 1, 1, 1};`，一个最直观的写法如下：

C

```
// 哲学家 i 的执行流程（编号 0 ~ 4）
while (1) {
    think();                        // 思考
    P(chopstick[i]);                // 拿左手边的筷子
    P(chopstick[(i + 1) % 5]);      // 拿右手边的筷子
    eat();                          // 进餐
    V(chopstick[i]);                // 放下左手边的筷子
    V(chopstick[(i + 1) % 5]);      // 放下右手边的筷子
}
```

#### 死锁是如何形成的？

如果 5 位哲学家**同时饥饿**，并且各自先拿起了自己左手边的筷子：

1. 此时 5 根筷子的信号量全都执行了一次 P 操作，其数值从 1 变成了 0。
2. 紧接着，每位哲学家试图去拿自己右手边的筷子时，发现右手边的筷子已被右侧邻居持有（信号量为 0，再执行 P 操作后变为 -1）。
3. **结果**：每位哲学家各持有一根筷子不放，同时等待右边的人释放筷子，形成了闭环等待链。所有哲学家都进入阻塞队列，谁也吃不上饭，系统陷入**永久死锁（Deadlock）**。

该场景完美复现了产生死锁的全部四个必要条件：

- **互斥**：一根筷子只能一人使用。
- **不可剥夺**：不能强行剥夺别人手里的筷子。
- **请求与保持**：持有一根筷子，同时申请另一根筷子。
- **循环等待**：进程间形成了环状的资源等待关系。

### 4. 常见的破除死锁方案

操作系统针对该问题有几种经典的解决方案，各自破坏了不同的死锁必要条件：

1. **破坏“请求与保持”（原子分配 / AND 型信号量）**：

   - 规定哲学家要么**同时拿起两根筷子**，要么**一根都不拿**。这正是前面提到的 AND 型信号量应用场景：

     $$Swait(chopstick_i, chopstick_{(i+1)\%5})$$

2. **破坏“循环等待”（资源偏序策略）**：

   - 规定奇数号哲学家先拿左手筷子、再拿右手筷子；偶数号哲学家先拿右手筷子、再拿左手筷子。
   - 相邻的奇偶哲学家会同时竞争同一根筷子，胜者拿到一根，败者直接阻塞，破坏了对称环路。

3. **控制并发规模（鸽巢原理）**：

   - 引入一个计数信号量 `semaphore count = 4;`，最多只允许 4 位哲学家同时去争夺筷子。5 根筷子分给最多 4 个人，必然至少有一位哲学家能同时拿到两根筷子完成进餐，从而打破死锁。

### 例题解析：4×100 接力赛同步过程



#### 1. 进程划分与前趋关系分析

接力赛共有 4 位运动员，分别对应 4 个并发进程 $P_1, P_2, P_3, P_4$。 各进程之间没有临界资源的互斥争夺，只有严格的**先后时序依赖（同步制约关系）**：   

$$P_1 \text{ 跑完 100 米} \longrightarrow P_2 \text{ 起跑} \longrightarrow P_2 \text{ 跑完 100 米} \longrightarrow P_3 \text{ 起跑} \longrightarrow P_3 \text{ 跑完 100 米} \longrightarrow P_4 \text{ 起跑}$$

#### 2. 信号量设计与物理意义

同步问题的核心原则是：**“前置操作完成后执行 V 操作（发信号），后置操作启动前执行 P 操作（等信号）”**。 需要设置 3 个记录型信号量充当“交接棒”：   

- **$S_{12}$**：表示第 1 棒到第 2 棒的交接状态。初值设为 **$0$**（比赛开始前，第 1 棒尚未交接）。   
- **$S_{23}$**：表示第 2 棒到第 3 棒的交接状态。初值设为 **$0$**。   
- **$S_{34}$**：表示第 3 棒到第 4 棒的交接状态。初值设为 **$0$**。   

#### 3. 信号量取值范围分析

以记录型信号量 $S_{12}$ 为例（$S_{23}$ 与 $S_{34}$ 同理）：

- **初始状态**：$S_{12} = 0$。   
- **$P_2$ 试图先跑**：若调度器先执行 $P_2$，它调用 $P(S_{12})$，变量执行减 1 操作后为 **$-1$**，发现 $< 0$，$P_2$ 自行阻塞挂起在等待队列。   
- **$P_1$ 跑完交棒**：$P_1$ 调用 $V(S_{12})$，变量执行加 1 操作：
  - 若此前 $P_2$ 已在队列等待（当前为 $-1$），加 1 后变为 **$0$**，并唤醒 $P_2$；
  - 若 $P_1$ 极快跑完而 $P_2$ 尚未执行 $P$ 操作（当前为 $0$），加 1 后变为 **$1$**。
- **结论**：每个信号量的取值范围为 **$\{-1, 0, 1\}$**（若按仅考虑无阻塞执行的整型信号量模型，取值为 $\{0, 1\}$）。

#### 4. 算法代码描述



C

```
semaphore S12 = 0;  // 1棒向2棒交接
semaphore S23 = 0;  // 2棒向3棒交接
semaphore S34 = 0;  // 3棒向4棒交接

cobegin
process P1 {
    跑100米;
    V(S12);         // 交棒给第2棒
}

process P2 {
    P(S12);         // 等待第1棒交棒
    跑100米;
    V(S23);         // 交棒给第3棒
}

process P3 {
    P(S23);         // 等待第2棒交棒
    跑100米;
    V(S34);         // 交棒给第4棒
}

process P4 {
    P(S34);         // 等待第3棒交棒
    跑100米;
}
coend
```

   

### 为你出的练习题：公共汽车“司机与售票员”同步问题

**题目描述**：

在公共汽车运行过程中，司机和售票员各司其职，其协同动作如下：

- **司机进程**：启动车辆 $\to$ 正常驾驶 $\to$ 到站停车。
- **售票员进程**：关车门 $\to$ 售票 $\to$ 开车门。

**同步约束**：

1. 必须由售票员关好车门后，司机才能启动车辆。
2. 汽车行驶期间不能开车门，必须由司机到站停车后，售票员才能开车门。
3. 该过程循环往复。

**你的任务**：

1. 说明需要设置哪些信号量、各信号量的**初值**及其**物理含义**。
2. 说明信号量的**取值范围**。
3. 编写用 PV 操作实现司机与售票员同步的伪代码。

这道题既不是 2 个，也不是 3 个信号量，而是严格需要 **4 个信号量**。

你的手写解答已经抓住了“消费者等零件”这一侧的同步逻辑，但在**防止缓冲区溢出**以及**P 操作与动作的执行顺序**上存在严重错误。

### 一、为什么不能是 2 个或 3 个？（学术纠偏）

#### 1. 为什么 2 个信号量是错误的？

在你的手写代码中：

- 进程 $P_1$ 的循环内部只有 `生产A; V(sem_buffer1);`，完全没有 `P` 操作。
- **致命问题（缓冲区溢出）**：题目明确规定“暂存架容量为 1，架子满了不能继续放”。如果 $P_1$ 执行得比 $P_3$ 快，在 $P_3$ 还没来得及取走零件时，$P_1$ 会连续循环执行，把第 2 个、第 3 个零件强行塞进容量只有 1 的暂存架中，导致暂存架溢出。
- **结论**：你设置的 2 个信号量只能解决“**架子空了不能取**”（通知 $P_3$），却无法限制“**架子满了不能放**”（限制 $P_1, P_2$）。要限制生产，必须给每个架子补充一个表示“空闲槽位数”的信号量。

#### 2. 为什么 3 个信号量也不够？

车间里有两个**完全独立**的暂存架（$\text{Buffer}_1$ 和 $\text{Buffer}_2$）：

- $\text{Buffer}_1$ 的放与取是一组前趋制约；

- $\text{Buffer}_2$ 的放与取是另一组前趋制约。

  两个架子互不干扰，不能共用一个“空位”信号量，否则会导致逻辑混乱（例如 $\text{Buffer}_1$ 满了，却因为共用计数器导致 $P_2$ 也无法向 $\text{Buffer}_2$ 放零件）。因此，每个架子各需要 2 个信号量（1 个管“空位”，1 个管“满位”），共计 **4 个**。

### 二、手写答案中的其他问题诊断

#### 1. 进程 $P_3$ 中 P 操作的次序颠倒（致命错误）

你在 $P_3$ 中写的是：

C

```
取A;
P(sem_buffer1);
```

- **这是严重的因果倒置**：必须**先检查并等待**架子上有零件（执行 `P` 操作），确保拿到了资源，**才能执行**物理动作“从架子上取 A”。
- 如果像你代码中那样先执行“取 A”，当架子是空的时候，进程已经去摸了空架子，之后才执行 `P` 陷入阻塞，在逻辑上完全违背了同步保护的意义。

#### 2. 信号量取值范围

引入 4 个信号量后，因为每个暂存架容量为 1，且每个信号量只由 1 个进程生产、1 个进程消费，其取值范围均为 **$\{-1, 0, 1\}$**。

### 三、标准参考解答

#### 1. 信号量定义与初值

- **`empty1 = 1`**：表示 $\text{Buffer}_1$ 的空位数，初值为 1（初始时架子为空，允许放 1 个零件 A）。
- **`full1 = 0`**：表示 $\text{Buffer}_1$ 中零件 A 的数量，初值为 0（初始时没有零件 A）。
- **`empty2 = 1`**：表示 $\text{Buffer}_2$ 的空位数，初值为 1（初始时架子为空，允许放 1 个零件 B）。
- **`full2 = 0`**：表示 $\text{Buffer}_2$ 中零件 B 的数量，初值为 0（初始时没有零件 B）。

#### 2. 取值范围

四个信号量的取值范围均为 **$\{-1, 0, 1\}$**。

#### 3. 算法描述

C

```
semaphore empty1 = 1;  // Buffer1 空闲槽位
semaphore full1 = 0;   // Buffer1 中零件A数量
semaphore empty2 = 1;  // Buffer2 空闲槽位
semaphore full2 = 0;   // Buffer2 中零件B数量

cobegin
process P1 {
    while (true) {
        生产零件A;
        P(empty1);             // 1. 申请 Buffer1 的空位（若已满则在此阻塞）
        将零件A放入Buffer1;
        V(full1);              // 2. 通知 P3：Buffer1 中有零件 A 了
    }
}

process P2 {
    while (true) {
        生产零件B;
        P(empty2);             // 1. 申请 Buffer2 的空位（若已满则在此阻塞）
        将零件B放入Buffer2;
        V(full2);              // 2. 通知 P3：Buffer2 中有零件 B 了
    }
}

process P3 {
    while (true) {
        P(full1);              // 1. 等待 Buffer1 中有零件 A
        从Buffer1中取出零件A;
        V(empty1);             // 2. 释放 Buffer1 的空位，通知 P1 可以继续生产

        P(full2);              // 3. 等待 Buffer2 中有零件 B
        从Buffer2中取出零件B;
        V(empty2);             // 4. 释放 Buffer2 的空位，通知 P2 可以继续生产

        将零件A和零件B组装成成品;
    }
}
coend
```

*(注：由于 $\text{Buffer}_1$ 与 $\text{Buffer}_2$ 容量为 1，且各自只有一个生产者和一个消费者，在严格的 `empty` / `full` 同步制约下已经保证了对缓冲区的互斥访问，无需额外添加互斥信号量 `mutex`。)*



## 也就是在同步问题中，不仅全局需要出现成对信号量，每个进程中也必须既有V也有P？

**并不是。在同步问题中，绝不要求每个进程内部都必须既有 P 又有 V。**

一个进程内部是否包含 P 或 V，完全取决于该进程在前趋图（依赖关系网）中所处的**位置与角色**。

### 1. 反例验证：回顾 4×100 接力赛

请直接看你们课件的第一道例题（4×100 接力赛）：

- **进程 $P_1$（第一棒）**：

  C

  ```
  跑100米;
  V(S12);   // 只有 V，没有任何 P！
  ```

  因为比赛一开始第一棒就可以直接起跑，不需要等待任何前置信号，所以它**没有 P 操作**。

- **进程 $P_4$（第四棒）**：

  C

  ```
  P(S34);   // 只有 P，没有任何 V！
  跑100米;
  ```

  因为第四棒冲过终点后比赛就结束了，后面没有任何人需要等待它发出信号，所以它**没有 V 操作**。

这充分证明：**单向执行的前趋同步中，源头进程只有 V，终点进程只有 P。**

### 2. 为什么刚才的“零件组装”中每个进程都有 P 和 V？

你在上一题中看到每个进程既有 P 又有 V，是因为那道题具备两个特殊特征：**“容量有限”\**与\**“无限循环（while(true)）”**，从而构成了**双向闭环制约**：

1. **正向同步（零件依赖）**：
   - $P_1$ 生产零件 $\to$ $P_3$ 消耗零件。
   - 这里 $P_1$ 是前驱（执行 `V(full1)`），$P_3$ 是后继（执行 `P(full1)`）。
2. **反向同步（空间依赖）**：
   - 暂存架容量只有 1，不是无限大的。$P_1$ 要放新零件，必须等 $P_3$ 把旧零件拿走腾出空位。
   - 这里 $P_3$ 成了前驱（执行 `V(empty1)` 腾出空间），$P_1$ 成了后继（执行 `P(empty1)` 等待空间）。

因为存在这层“你等我的零件，我等你的空位”的双向循环依赖，每个进程既扮演了前驱又扮演了后继，所以代码中才同时出现了 P 和 V。

### 3. 判断进程是否需要 P / V 的通用准则

在分析并发同步问题时，可以通过**前趋图的入度与出度**来快速判定：

| **进程在前趋图中的角色** | **特征**                                                 | **信号量操作配置** | **典型代表**                                  |
| ------------------------ | -------------------------------------------------------- | ------------------ | --------------------------------------------- |
| **纯源头进程（Source）** | **无入度，有出度**（不依赖任何人，只通知别人）           | **只有 V**         | 接力赛第 1 棒、纯单向无界生产者               |
| **纯终点进程（Sink）**   | **有入度，无出度**（依赖别人，不需要通知任何人）         | **只有 P**         | 接力赛第 4 棒、纯单向消费者（任务完成即终止） |
| **中间传递进程**         | **既有入度，又有出度**（等前面的做完，做完通知后面的）   | **既有 P，也有 V** | 接力赛第 2、3 棒                              |
| **闭环循环系统**         | **图中有环路**（互相依赖，如有限缓冲区的循环生产与消费） | **既有 P，也有 V** | 生产者-消费者问题、读者-写者问题              |
