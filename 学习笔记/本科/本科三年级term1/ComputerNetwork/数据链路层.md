# 数据链路层

## PPP 

**PPP（Point-to-Point Protocol，点对点协议）** 是数据链路层针对点对点信道（全双工物理链路，只有两个端点通信，无任何第三方冲突竞争）设计的标准协议。

与以太网广播信道需要复杂的介质访问控制（如 CSMA/CD）不同，点对点信道天然不存在“碰撞”与“信道争用”，因此 PPP 的设计核心聚焦于**封装成帧、链路状态协商与多网络层支持**。

### 一、 PPP 协议的三大支柱构架

PPP 并非单一协议，而是一整套模块化的协议簇，由三部分组成：

1. **成帧方法（Framing）**：

   借用 HDLC（高级数据链路控制）的成帧思想，定义了数据如何被包裹在帧头与帧尾标志之间，并在帧尾提供 CRC 循环冗余校验。

2. **LCP（Link Control Protocol，链路控制协议）**：

   负责**数据链路本身的建立、配置、测试与拆除**。

   - 双方在传输用户数据之前，先用 LCP 协商基本链路参数（如最大传输单元 MTU、是否启用身份鉴权认证）。
   - 常见的认证协议包括 PAP（明文两次握手）与 CHAP（基于 MD5 挑战-应答的三次握手）。

3. **NCP（Network Control Protocol，网络控制协议族）**：

   负责**协商和配置链路之上的网络层协议**。

   - PPP 具有良好的多协议支持能力，可以在同一条物理链路上承载 IPv4、IPv6 等不同网络层协议。
   - 最典型的 NCP 是 **IPCP（IP Control Protocol）**：家用宽带拨号（PPPoE）成功后，运营商就是通过 IPCP 协议为路由器的 WAN 口动态下发公网/私网 IP 地址和 DNS 服务器地址。

### 二、 PPP 帧的标准结构

PPP 帧的格式固定为字节对齐结构（总共占用 6 ~ 8 个字节的开销）：

Plaintext

```
+----------+----------+----------+-----------------+-----------------------+----------+----------+
|  标志 F  |  地址 A  |  控制 C  |    协议 Protocol |    信息载荷 (Payload)  |  校验 FCS |  标志 F  |
| (1 字节) | (1 字节) | (1 字节) |   (1 或 2 字节)  |    (0 ~ 1500 字节)    | (2 字节) | (1 字节) |
+----------+----------+----------+-----------------+-----------------------+----------+----------+
```

- **标志字段（Flag，F）**：固定为 `0x7E`（二进制 `01111110`），作为一帧的起始和结束边界。
- **地址字段（Address，A）**：固定为 `0xFF`。
  - *原因*：由于链路两端只有通信双方两个节点，根本不需要像以太网那样通过 MAC 地址来路由转发，`0xFF` 是沿袭 HDLC 广播地址的虚拟占位符。
- **控制字段（Control，C）**：固定为 `0x03`。
  - 表示该帧为无序号信息帧（Unnumbered Information），不提供编号与滑动窗口确认。
- **协议字段（Protocol）**：标识净荷部分装载的是什么类型的数据。
  - `0x0021`：IP 数据报。
  - `0xC021`：LCP 链路控制数据。
  - `0x8021`：IPCP 网络控制数据。
  - `0xC223`：CHAP 认证报文。
- **信息字段（Information）**：上层数据载荷，默认最大长度（MTU）通常为 1500 字节。
- **帧校验序列（FCS）**：通常为 16 位（2 字节）或 32 位（4 字节）的 CRC 校验码，用于检测突发物理差错。

### 三、 透明传输机制（解决数据中的 0x7E 冲突）

如果用户上传的图片或程序二进制数据中恰好包含 `0x7E`，接收端网卡在解析时就会误以为帧提前结束。为了实现“透明传输”（即任何比特组合的数据都能无损通过），PPP 针对不同的底层物理信道设计了两种处理方案：

#### 1. 异步传输（按字节处理）：字节填充法（Byte Stuffing）

当通信线路是异步传输（例如通过串口传输，逐字节接收）时，PPP 定义转义字节为 `0x7D`（二进制 `01111101`），执行**字节替换**规则：

- **数据中出现 `0x7E`**：转换为 2 字节序列 **`0x7D, 0x5E`**。
  - *数学映射*：`0x7E` 异或 `0x20` 得到 `0x5E`。
- **数据中出现转义符本身 `0x7D`**：转换为 2 字节序列 **`0x7D, 0x5D`**。
  - *数学映射*：`0x7D` 异或 `0x20` 得到 `0x5D`。
- **数据中出现 ASCII 控制字符（如数值小于 `0x20`）**：若需避开某些硬件控制字符，也可将其在前面加上 `0x7D`，并将原字符异或 `0x20` 进行转义。
- **接收端逆操作**：收到 `0x7D` 时直接丢弃该转义字节，将其后的下一个字节异或 `0x20`，无损还原出原始数据。

#### 2. 同步传输（按连续位流处理）：零比特填充法（Bit Stuffing）

当通信线路是同步传输（例如 SONET/SDH 光纤网络，连续无间隙传输比特流）时，硬件逐比特扫描数据，执行“逢五插零”规则：

- **发送端规则**：
  - 硬件检测发送数据流，一旦发现连续出现 **5 个连续的 `1`**（`11111`），**无论后面紧跟的是什么，都无条件在第 5 个 `1` 后面强行插入一个 `0`**。
  - 由于定界标志 `0x7E` 的特征是连续 6 个 `1`（`01111110`），数据流内部经过此项操作后，连续 `1` 的数量最多只能达到 5 个，**从根本上杜绝了在帧内部伪造出 `0x7E` 的可能性**。
- **接收端规则**：
  - 硬件扫描比特流，一旦发现连续 5 个 `1`，立即检查其紧邻的下一位：
    - 如果下一位是 `0`：说明这是发送端填充的垃圾位，硬件**直接将其删除并恢复原始数据**；
    - 如果下一位是 `1` 且再下一位是 `0`（即 `01111110`）：判定找到了**帧边界标志**；
    - 如果下一位是 `1` 且再下一位还是 `1`（连续 7 个 `1`）：判定为信道物理错误或线路处于空闲标记状态。

### 四、 PPP 的设计哲学与局限

- **简单至上，只检错不纠错**：

  收到受损帧后通过 FCS 检出，直接丢弃，不发送 NAK，也不请求重传；

- **无流量控制**：

  没有滑动窗口机制，数据发送速率由物理层与上层 TCP 自行调节；

- **点对点专享**：

  不支持总线型多路访问，因此不具备介质争用与冲突解决能力。

## 填充法

**数据链路层的核心基本问题只有三个：“字节填充”只是实现“透明传输”的一种具体工程手段。**

**封装成帧、透明传输、差错检测**是数据链路层要解决的**三大核心问题（目标）**；而**字节填充**与**零比特填充**，是为了解决**透明传输**这个核心问题所采用的**技术方案（手段）**。

### 一、 概念层级澄清：目标与手段

| **数据链路层的三大核心问题（目标）**       | **对应的工程挑战**                                           | **解决该问题的具体实现手段**                                 |
| ------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **1. 封装成帧 (Framing)**                  | 如何在无始无终的数据流中划分出独立的一帧？                   | 在数据前后加上**帧头（SOH）**与**帧尾（EOT / Flag）**作为定界标志（如 PPP 的 `0x7E`）。 |
| **2. 透明传输 (Transparent Transmission)** | 用户数据里如果恰好包含和定界标志一模一样的字节/比特，接收端如何不误判为帧提前结束？ | • **面向字节链路**：使用 **字节填充（Byte Stuffing）**  • **面向比特链路**：使用 **零比特填充（Bit Stuffing，逢五插零）** |
| **3. 差错检测 (Error Detection)**          | 物理线路受到电磁干扰发生比特翻转，接收端如何发现损坏并丢弃？ | **CRC（循环冗余检验）**、奇偶校验、校验和（Checksum）。      |

### 二、 彻底搞懂“字节填充”：用编程语言的“转义字符”秒懂

很多教材把字节填充讲得玄乎其玄，但它的本质就是 C/C++ 或 Python 字符串里的**转义字符（`\`）机制**。

#### 1. 编程中的类比

在 C 语言中，双引号 `"` 用来标记字符串的开始和结束（这叫**封装成帧**）：

C

```
char str[] = "hello"; // 编译器通过首尾的 " 知道字符串边界
```

如果你的字符串内容本身包含双引号，比如你想保存 `say "hello"`，你会怎么写？

C

```
char str[] = "say \"hello\""; // 编译器通过 \" 知道这不是结束，而是普通字符
```

如果你本身想打出一个反斜杠 `\`，你会怎么写？

C

```
char str[] = "say \\"; // 编译器通过 \\ 知道这是一个普通的反斜杠
```

#### 2. PPP 字节填充与转义的完全对应

在 PPP 协议的异步传输中：

- **帧定界符** 是 `0x7E`，相当于 C 语言里的 **`"`**。
- **转义字节** 是 `0x7D`，相当于 C 语言里的 **`\`**。

发送端网卡硬件在扫描数据区时，执行极其简单的替换规则：

1. **如果在数据中看到了 `0x7E`**（相当于看到了 `"`）：
   - 发送端绝不能直接发 `0x7E`，否则接收端一看到就以为帧到头了。
   - **处理**：先发一个转义符 `0x7D`，再把 `0x7E` 异或 `0x20` 变成 `0x5E`，合并发出去：**`0x7D, 0x5E`**。
   - *注：`0x7E ^ 0x20 = 0x5E`，异或 `0x20` 的目的纯粹是为了把第 6 位翻转，让它彻底不像 `0x7E`。*
2. **如果在数据中看到了转义符本身 `0x7D`**（相当于看到了 `\`）：
   - 必须把这个转义符也保护起来，不能让接收端误以为它是转义指令。
   - **处理**：发一个转义符 `0x7D`，再把 `0x7D` 异或 `0x20` 变成 `0x5D`，合并发出去：**`0x7D, 0x5D`**。

### 三、 完整数据流传输全流程示例

假设上层应用传递给网卡一段 payload 数据，字节内容为：

$$\text{原始数据：} [\text{A}] \quad [\mathbf{0x7E}] \quad [\text{B}] \quad [\mathbf{0x7D}] \quad [\text{C}]$$

**1. 发送端处理（封装成帧 + 字节填充）**：

- 加上帧头：`0x7E`

- 处理数据：

  - `A` $\to$ `A`
  - `0x7E` $\to$ 转义为 `0x7D, 0x5E`
  - `B` $\to$ `B`
  - `0x7D` $\to$ 转义为 `0x7D, 0x5D`
  - `C` $\to$ `C`

- 加上帧尾：`0x7E`

- **线路上实际跑的字节流**：

  $$\mathbf{0x7E} \quad [\text{A}] \quad [\mathbf{0x7D}, \mathbf{0x5E}] \quad [\text{B}] \quad [\mathbf{0x7D}, \mathbf{0x5D}] \quad [\text{C}] \quad \mathbf{0x7E}$$

**2. 接收端处理（去转义 + 恢复数据）**：

- 读到第 1 个 `0x7E`：识别为**帧起始**，开始收取数据；
- 读到 `A`：写入内存缓冲；
- 读到 `0x7D`：发现是**转义标记**，**丢弃该 `0x7D`**，并将其后面紧跟的 `0x5E` 异或 `0x20` 还原为 `0x7E` 写入内存；
- 读到 `B`：写入内存缓冲；
- 读到 `0x7D`：发现是**转义标记**，**丢弃该 `0x7D`**，并将其后面紧跟的 `0x5D` 异或 `0x20` 还原为 `0x7D` 写入内存；
- 读到 `C`：写入内存缓冲；
- 读到最后一个 `0x7E`：识别为**帧结束**。

最终内存中解出的数据与原始数据完全一致：`A, 0x7E, B, 0x7D, C`。用户数据哪怕含有任意特殊字符，都能像在透明玻璃中穿过一样毫无阻碍，这就是“**透明传输**”。

## CSMA/CD

**CSMA/CD（Carrier Sense Multiple Access with Collision Detection，载波监听多路访问/碰撞检测）** 是经典以太网（共享总线型、半双工网络）在数据链路层 MAC（介质访问控制）子层的核心协议。

与 PPP 独占一条点对点物理链路不同，早期以太网是多台主机共同挂载在一根同轴电缆上。CSMA/CD 的本质是用一套分布式的竞争规则，解决“多人在同一个房间里争抢发言权”的协调问题。

其运作流程可以高度概括为十六字口诀：**先听后发，边发边听，冲突停发，随机重发**。

### 一、 协议名词的四个物理动作分解

1. **MA（Multiple Access，多路访问 / 多点接入）**：
   - 许多计算机以多点接入的方式连接在同一根总线上，信道是共享的广播信道。
2. **CS（Carrier Sense，载波监听 / “先听后发”）**：
   - 任何站点在准备发送数据前，必须先用硬件检测总线上是否有其他站点在发送信号（即检测线路上的电平电压波动）。
   - **若信道忙**：推迟发送，持续监听直到信道空闲。
   - **若信道闲**：等待一个帧间最小间隔（96 比特时间，用于清理上一次传输的残存状态并让接收硬件复位）后立即发送。
3. **CD（Collision Detection，碰撞检测 / “边发边听”）**：
   - 即使“先听后发”，两个站点依然可能同时发信导致电磁波在总线上相遇，造成信号电压叠加变形（即**碰撞 / 冲突**）。
   - 站点在发送数据的同时，网卡芯片必须持续监测总线电平。当总线上的电压波动幅度超过正常发送单路信号的阈值时，网卡立即判定“发生了碰撞”。
4. **冲突停发与人为干扰信号（Jamming Signal）**：
   - 一旦检测到碰撞，站点必须**立刻停止继续发送该数据帧**（避免浪费信道带宽）。
   - 同时，网卡会向总线发送一段 **32 ~ 48 比特的人为干扰信号（Jamming Signal）**。目的在于强化冲突电平，确保总线上的所有其他相关站点都能明确知晓碰撞已经发生。

### 二、 核心物理矛盾：既然先听了，为什么还会碰撞？

**根本原因在于：电磁波在物理介质中的传播速率是有限的（存在传播时延 $\tau$）。**

电磁波在铜质双绞线或同轴电缆中的传播速度大约为光速的 $2/3$，即：

$$v \approx 2 \times 10^8 \text{ m/s} = 200 \text{ m/\mu s}$$

设总线两端最远的两个站点 A 和 B 之间的单向传播时延为 $\tau$：

1. $t = 0$ 时刻，A 监听总线为空闲，开始向外发送一个帧；
2. A 发出的电磁波信号正在以 $200 \text{ m/\mu s}$ 的速度在同轴电缆中向前推进；
3. 在 $t = \tau - \epsilon$ 时刻（信号马上就要到达 B 的前一瞬间），B 也准备发数据。B 监听总线，由于 A 的信号尚未抵达 B 端，**B 误以为信道完全空闲**，于是 B 也开始发送数据；
4. 几乎在刚发出的一瞬间，A 和 B 的信号在靠近 B 的电缆处迎面相撞，产生不可逆的波形畸变；
5. B 很快感知到碰撞，停止发送；但对于 A 而言，碰撞后的畸变波形还需要再经过大约 $\tau$ 的时间才能传回 A 端。
6. A 最终感知到碰撞的时刻接近 $t = 2\tau$。

### 三、 争用期（Contention Period）与最小帧长的数学推导

#### 1. 争用期 $2\tau$（碰撞窗口）

通过上述推导可知：**一个站点在发送数据后，最多需要经过 $2\tau$（两倍端到端单向传播时延，即往返传播时延 RTT）的时间，才能完全确定该帧是否遭遇了碰撞。**

- 这段时长 $2\tau$ 在以太网标准中被称为**争用期（碰撞窗口）**。
- 只要一个站点发完数据经过了 $2\tau$ 时长而没有检测到冲突，就意味着它的信号已经覆盖了整条总线，该帧后续将**绝对不会再遭遇碰撞**（赢得了本次信道的使用权）。

#### 2. 为什么必须有“最小帧长”？

如果一个帧非常短，发送端 A 还没等到反弹回来的碰撞信号，就已经把整个数据帧发送完毕并从网卡缓冲中清空了：

- A 会单方面认为“该帧发送圆满成功”；
- 但实际上，这帧在半路早就被撞成碎片了，接收端只能收到残缺信号并丢弃；
- 这就彻底违背了“发送端自己检测并处理冲突”的设计底线。

**定理**：**数据帧的发送时延（$T_{\text{frame}}$）必须大于或等于端到端的争用期（$2\tau$）**。

$$T_{\text{frame}} = \frac{L}{C} \ge 2\tau \implies L_{\min} = C \times 2\tau$$

（其中 $L$ 为帧长（bit），$C$ 为信道数据传输速率（bps））。

#### 3. 经典以太网 64 字节的由来

在早期的 10 Mbps 经典以太网标准（IEEE 802.3）中：

- 规定最长物理跨度为通过 4 个中继器连接的 5 段电缆（约 2500 米），加上中继器内部的时延放大，算得最大的 $2\tau \approx 51.2\ \mu\text{s}$。

- 最小帧长为：

  $$L_{\min} = 10\text{ Mbps} \times 51.2\ \mu\text{s} = 10 \times 10^6 \times 51.2 \times 10^{-6}\text{ bit} = 512\text{ bit} = \mathbf{64\text{ 字节}}$$

- **工程结论**：

  - 以太网中任何有效帧的长度**绝不能小于 64 字节**。如果上层 IP 数据报太小，数据链路层必须在尾部强制填充全 0 的填充字段（Padding）补齐至 64 字节。
  - 接收网卡只要在电缆上收到长度小于 64 字节的帧，直接断定为“碰撞碎片帧（Runt Frame）”，就地物理丢弃。

### 四、 冲突解决：截断二进制指数退避算法（Binary Exponential Backoff）

当站点检测到碰撞并发出干扰信号后，不能立刻重发，否则会陷入死循环碰撞。它采用**动态随机退避算法**：

1. **基本退避时间单位**：取争用期 $2\tau$（在 10 Mbps 以太网中即为 $51.2\ \mu\text{s}$，也称为一个时间片 Slot Time）。

2. **确定参数 $k$**：

   $$k = \min[\text{重传次数}, 10]$$

3. **在离散整数集合中随机抽取等待片数 $r$**：

   $$r \in \{0, 1, 2, \dots, 2^k - 1\}$$

4. **推迟时间**：

   $$T_{\text{backoff}} = r \times 2\tau$$

5. **截断与中止**：

   - 当重传次数超过 10 次时，$k$ 不再增加，固定为 10（随机窗口上限锁死在 $2^{10}-1 = 1023$ 个时间片，防止等待时间无限拉长，此即“截断”）。
   - 若重传达到 **16 次** 依然遭遇碰撞，说明信道拥堵极其严重或总线物理断裂，网卡**彻底放弃重发**，直接向网络层报错丢包。

### 五、 现代网络视角：CSMA/CD 的现状

在现代以太网中，由双绞线/光纤构成的网络已经演进为**通过交换机连接的“全双工（Full-Duplex）点对点通信”**：

- 物理介质中，一根线专门负责接收（RX），另一根线专门负责发送（TX），且交换机内部具备帧缓冲机制；
- 两个方向的数据互不干扰，**物理碰撞已经彻底不复存在**；
- 因此，在现代千兆、万兆以太网中，**CSMA/CD 机制已被完全关闭**，现代以太网在物理运行上已退化为由交换机隔离的无冲突点对点网络。但作为理解 MAC 控制、争用期 $2\tau$ 及 64 字节最小帧长历史渊源的载体，它依然是计算机网络的核心基础。

## MAC

以太网 MAC（Medium Access Control）子层处于数据链路层的下半部分，直接面向物理层。它主要负责两大核心任务：**通过硬件地址对节点进行物理寻址**，以及**将上层网络层数据报封装为符合以太网规范的 MAC 帧**。

### 一、 MAC 硬件地址（EUI-48）的内部二进制结构

MAC 地址长度为 **48 位（6 字节）**，通常以 12 位十六进制数表示（如 `00-1A-2B-3C-4D-5E` 或 `00:1A:2B:3C:4D:5E`）。

在逻辑结构上，它被划分为两大部分，但其**第一个字节的最低两个比特位**具有特殊的协议控制意义：

Plaintext

```
+-----------------------------------+-----------------------------------+
|      前 24 位：OUI 厂商代码       |       后 24 位：扩展标识符        |
|     (由 IEEE 统一分配给厂商)      |       (由厂商自行分配给网卡)      |
+-----------------------------------+-----------------------------------+
       |
       +--> 深入展开第一个字节（8 bit）：
            [ b7  b6  b5  b4  b3  b2  b1  b0 ]
                                       |   |
                                       |   +-- I/G 位 (Individual / Group)
                                       +------ U/L 位 (Universal / Local)
```

#### 1. I/G 位（Individual / Group，单播/组播标志位）

- **位于第 1 个字节的最低有效位（b0）**（以太网在物理线上按字节串行传输时，该位是**第一个被发送到信道上的比特**）。
- **b0 = 0**：**单播地址（Individual）**。代表一台物理网卡的唯一硬件接口。
- **b0 = 1**：**多播 / 组播 / 广播地址（Group）**。代表一组设备的逻辑集合。

#### 2. U/L 位（Universal / Local，全局/本地管理位）

- **位于第 1 个字节的倒数第二位（b1）**。
- **b1 = 0**：**全球管理（Universal）**。由 IEEE 正式分配 OUI，保证全球唯一。
- **b1 = 1**：**本地管理（Local）**。由本地网络管理员自定义设置，或由操作系统动态随机生成（如手机虚拟 MAC、虚拟机虚拟网卡），IEEE 不保证其唯一性。

### 二、 单播、多播（组播）与广播的底层判定与处理机制

以太网是广播介质或全双工交换网络。网卡物理芯片（PHY/MAC）接收到信道上的电信号并完成反序列化后，会通过**硬件地址过滤引擎**对目的 MAC 地址进行瞬时判定：

#### 1. 单播（Unicast，一对一）

- **特征**：目的 MAC 的 I/G 位为 `0`（例如 `00:0C:29:XX:XX:XX`）。
- **硬件处理**：
  - 网卡接收到帧后，硬件比较“帧中的目的 MAC”与“本机 ROM/寄存器中烧录的 MAC”；
  - **完全一致**：产生硬件中断，将数据帧传入主存，交由操作系统网络栈处理；
  - **不一致**：网卡控制器直接在**硬件层面静默丢弃**，不消耗 CPU 的任何计算资源（除非网卡被设置为**混杂模式（Promiscuous Mode）**，如抓包工具 Wireshark 运行时，网卡会无条件收取信道上的所有单播帧）。

#### 2. 广播（Broadcast，一对所有）

- **特征**：48 位二进制全部为 `1`，十六进制固定为 **`FF-FF-FF-FF-FF-FF`**。
- **硬件处理**：
  - 广播是组播的一个极限特例（I/G 位显然为 1）。
  - 二层广播域内的**所有网卡硬件必须无条件接收该帧**，并必须向上提交给操作系统内核协议栈（典型应用：ARP 请求解析 IP 对应的 MAC、DHCP Discover 寻找路由器分配 IP）。

#### 3. 多播 / 组播（Multicast，一对一组）

- **特征**：I/G 位为 `1`，且非全 `1`。
- **硬件处理**： n
  - 网卡内部有一个可编程的多播哈希过滤表（Multicast Table）。
  - 只有当本机操作系统加入了某个组播组（例如加入视频会议组流），网卡才会把对应的多播 MAC 写入硬件过滤白名单；其余未订阅的多播帧直接在网卡硬件层丢弃。
- **典型映射机制（IPv4 组播映射）**：
  - IANA 将高 24 位固定为 **`01-00-5E`** 预留给 IPv4 组播。
  - 为了节约 OUI 地址块，第 25 位固定为 `0`，仅留出低 23 位用于映射 IPv4 组播地址。
  - **代数冲突细节**：IPv4 组播 IP 地址（D 类地址 `224.0.0.0 ~ 239.255.255.255`）有 28 个可变位，但映射到 MAC 地址时只有 23 位可用，因此有 $28 - 23 = 5$ 个比特位丢失。这导致**每 32 个不同的 IPv4 组播 IP 地址会映射到同一个 MAC 地址上**，接收端操作系统协议栈必须在网络层再次过滤不属于自己的组播包。

### 三、 以太网 MAC 帧结构（Ethernet II / RFC 894）

历史上存在两种 MAC 帧标准：DEC/Intel/Xerox 制定的 **Ethernet II（DIX Ethernet V2）** 与 IEEE 制定的 **802.3** 标准。现代互联网协议栈（TCP/IP）事实上的全球统一标准是 **Ethernet II**。

其标准物理传输结构如下：

Plaintext

```
物理层同步前导码（不计入 MAC 帧长）
+------------------------+-------------+
|    前导码 (Preamble)   | 帧首定界符  |
|         7 字节         |    (SFD)    |
|   10101010...10101010  |   1 字节    |
|       (共 56 bit)      |  10101011   |
+------------------------+-------------+

以太网 MAC 帧主体（总长度 64 ~ 1518 字节）
+---------------+---------------+---------------+-----------------------+---------------+
|    目的地址   |    源地址     |   类型 (Type) |    数据载荷 (Payload)  |   校验 (FCS)  |
|    (DA, 6B)   |   (SA, 6B)    |      (2B)     |   (46 ~ 1500 字节)    |      (4B)     |
+---------------+---------------+---------------+-----------------------+---------------+
```

#### 1. 物理层字段（由物理层 PHY 芯片自动追加/剥离）

- **前导码（Preamble，7 字节）**：连续 7 个 `0x55`（二进制 `10101010`）。用于使接收端网卡的时钟电路与发送端快速达成位同步（Bit Synchronization）。
- **帧首定界符（SFD，1 字节）**：固定为 `0xD5`（二进制 `10101011`）。末尾的连续两个 `1` 充当警报信号，通知接收芯片：“时钟同步结束，下一个比特开始是真实的 MAC 帧头”。
- *注：前导码和 SFD 是物理层的同步开销，**不计入以太网帧的标准长度计算**。*

#### 2. MAC 帧头与数据字段

- **目的 MAC 地址（6 字节）**：标识该帧送往哪个单播网卡、多播组或全网广播。

- **源 MAC 地址（6 字节）**：标识发送此帧的物理网卡单播硬件地址（必须是单播地址）。

- **类型字段（Type，2 字节）**：指示上层协议类型（网络层协议分流依据）：

  - `0x0800`：IPv4 数据报
  - `0x0806`：ARP 地址解析协议
  - `0x86DD`：IPv6 数据报
  - *(注：在 IEEE 802.3 规范中此字段被定义为“长度字段 Length”，数值 $\le 1500$；若该数值 $\ge 1536$（即 `0x0600`），则无条件判定为 Ethernet II 的 Type 字段。)*

- **数据载荷（Payload，46 ~ 1500 字节）**：

  - **最大长度 1500 字节**：这是以太网的经典 MTU（Maximum Transmission Unit）。

  - **最小长度 46 字节的由来**：由上一节推导的 CSMA/CD 争用期最小帧长 64 字节决定：

    $$\text{最小帧长} (64\text{ 字节}) - \text{目的地址} (6\text{B}) - \text{源地址} (6\text{B}) - \text{类型} (2\text{B}) - \text{FCS} (4\text{B}) = \mathbf{46\text{ 字节}}$$

    如果上层 IP 数据报长度不足 46 字节（例如空的 TCP ACK 报文只有 40 字节），MAC 子层必须强制在数据后填充全 0 补白字段（Padding）补齐至 46 字节。

- **帧校验序列（FCS，4 字节）**：

  - 采用 **CRC-32** 多项式算法，校验范围**覆盖从目的 MAC 地址开始到数据载荷/填充结束的所有字段**。

**全 F MAC 地址是标准的以太网广播地址，而全 0 MAC 地址则是未指定的保留/占位地址（无效物理地址）。**

两者在以太网协议栈中扮演着完全不同的角色：

### 一、 全 F 的 MAC 地址（`FF:FF:FF:FF:FF:FF`）：标准广播地址

1. **二进制与逻辑结构**：
   - 48 个比特位全部为 `1`（`11111111-11111111-...-11111111`）。
   - 第 1 个字节的最低位（I/G 位）为 `1`，代表组播/广播；次低位（U/L 位）为 `1`，代表本地管理。
2. **底层硬件处理行为**：
   - 当二层交换机收到**目的 MAC 为全 F** 的数据帧时，会将其视为广播帧，执行泛洪（Flooding）操作，原样转发到当前 VLAN 内除接收端口外的所有其他端口。
   - 局域网内的所有终端网卡芯片，一旦检测到目的 MAC 为全 F，**硬件过滤器必须无条件放行接收**，触发中断并将其提交给操作系统的网络协议栈处理。
3. **典型应用场景**：
   - **ARP 请求（ARP Request）**：主机 A 知道主机 B 的 IP 但不知道其 MAC，便以全 F 作为以太网帧头的目的 MAC 向全网喊话：“谁拥有该 IP 地址？请把你的 MAC 发给我。”
   - **DHCP 发现（DHCP Discover）**：新接入网络的主机尚未获取 IP，需要向全网广播寻找可用的 DHCP 服务器。
   - **WOL（Wake-on-LAN 网络唤醒）**：唤醒魔术包的头部通常由连续 6 字节的 `0xFF` 组成引导。
4. **合法性限制**：
   - 全 F 只能作为**目的 MAC 地址**出现，**严禁作为源 MAC 地址**出现在以太网帧中。如果交换机收到源 MAC 为全 F 的帧，会直接判定为畸形帧/攻击帧并丢弃。

### 二、 全 0 的 MAC 地址（`00:00:00:00:00:00`）：未指定 / 占位地址

1. **定义与物理属性**：
   - 48 个比特位全部为 `0`。
   - 在网络标准中，全 0 被定义为 **未指定地址（Unspecified Address）** 或 **空地址**。**全球任何符合规范的商用网卡，其出厂 ROM 烧录地址（BIA）绝不可能为全 0**。
2. **在协议中的主要作用（占位符）**：
   - **ARP 请求报文内部的 Target MAC 占位**：
     - 这里需要区分**以太网帧头**与**内部 ARP 报文载荷**：
     - 在发出 ARP 请求时，**以太网帧头的目的 MAC** 必须填 **`FF:FF:FF:FF:FF:FF`**（为了让交换机广播给所有人）；
     - 但在封装于帧内部的 **ARP 报文载荷** 中，有一个字段叫“目标硬件地址（Target Hardware Address, THA）”。由于发送方此刻就是不知道对方的 MAC，因此该字段通常直接用 **`00:00:00:00:00:00`** 来填充占位，表示“此项为空，待查询”。
   - **系统初始化默认值**：
     - 操作系统内核或单片机网络栈在尚未成功读取物理 EEPROM/网卡寄存器之前，内存中的 MAC 缓冲区通常会被初始化清零为全 0。
   - **ARP 缓存表项的不完整状态（Incomplete）**：
     - 主机发出了 ARP 请求但尚未收到回复，或者等待超时时，系统 ARP 表中该 IP 对应的物理地址通常会暂时标记为全 0 或 Incomplete。
3. **网络设备对全 0 帧的处理**：
   - **源 MAC 为全 0**：如果信道上出现源 MAC 为 `00:00:00:00:00:00` 的帧，现代网络设备（交换机、路由器）通常直接将其判定为非法报文（Bogus/Malformed Frame）并就地丢弃，防止对交换机的 MAC 地址转发表（CAM 表）造成污染。
   - **目的 MAC 为全 0**：网卡默认不会接收目的 MAC 为全 0 的单播帧（除非开启混杂模式进行流量捕获）。

### 总结对照

| **维度**         | **FF:FF:FF:FF:FF:FF**                  | **00:00:00:00:00:00**                        |
| ---------------- | -------------------------------------- | -------------------------------------------- |
| **标准角色**     | 二层全网广播地址                       | 未指定地址 / 空地址 / 占位符                 |
| **作为目的 MAC** | **合法且极其常用**（局域网广播寻址）   | **无实际通信意义**（单播给一个不存在的网卡） |
| **作为源 MAC**   | **绝对非法**                           | **绝对非法**（通常意味着配置未初始化或伪造） |
| **交换机行为**   | 泛洪（复制转发到除入端口外的所有端口） | 通常丢弃或不进行 MAC 学习                    |



## 扩展——集线器和交换机，碰撞域、广播域、回路、广播、交换表

在探讨以太网的扩展时，最自然的认知起点是物理层设备**集线器（Hub）\**以及由此衍生的\**碰撞域（Collision Domain）**。

### 一、 集线器（Hub）：物理层的多端口中继器

在以太网从早期的同轴电缆总线转向双绞线星形拓扑时，集线器（Hub）是第一代核心连接设备。

1. **工作层次**：
   - 严格工作在 **OSI 模型的物理层（第一层，L1）**。
   - 它**完全看不懂**以太网帧头、MAC 地址或 IP 地址，本质上就是一个带有多个插口的**多端口中继器（Multi-port Repeater）**。
2. **信号转发机制（纯物理电平复制）**：
   - 当集线器的端口 1 接收到某个网卡发来的电信号时，内部电路只做两件事：**整形放大（消除衰减和失真）** 与 **物理转发**。
   - 它会机械地将该电信号**广播发送给除端口 1 之外的所有其他端口**。
3. **性能特征**：
   - **共享带宽**：如果集线器的总带宽是 10 Mbps，连接了 8 台电脑，这 8 台电脑必须平摊这 10 Mbps 的传输能力，无法各自独享。
   - **强制半双工**：所有端口在物理电气层面是直接并联连通的，通信必须依赖 CSMA/CD 机制；同一瞬间只要有两个端口同时发送电信号，电平叠加就会发生碰撞。

### 二、 碰撞域（Collision Domain，冲突域）

**碰撞域**是指**在物理介质上，若两个或多个设备在同一时刻发送数据，会导致信号发生物理重叠碰撞并损坏的区域范围**。

1. **集线器与碰撞域的关系**：
   - **集线器不能隔离碰撞域，反而会扩大碰撞域**。
   - 所有连接在同一台集线器上的主机，都处于**同一个碰撞域**内。
   - 如果使用一根网线将两台 8 端口集线器级联起来，这 16 个端口上的所有设备将合并成一个**范围更大、情况更糟的单一碰撞域**。
2. **扩大碰撞域带来的工程灾难**：
   - 随着接入集线器的主机数量增加，多台主机同时准备发信的概率呈几何级数上升；
   - CSMA/CD 碰撞频繁触发，导致大量数据帧被撞碎重发，争用期退避时间剧增；
   - 当总线网络负载超过 30% ~ 40% 时，碰撞域内的有效数据吞吐量会急剧恶化，发生“网络雪崩”。

集线器仅在物理距离上扩展了网络覆盖，但在逻辑性能上将所有主机捆绑在同一个碰撞泥潭中。

为了解决集线器导致的“碰撞域无限扩大”与“共享带宽被瓜分”的致命缺陷，以太网引入了数据链路层的核心设备——**以太网交换机（Switch）**，其核心灵魂在于硬件维护的**交换表（Switch Table / MAC 地址表）**。

### 一、 以太网交换机（Switch）：链路层的多端口网桥

以太网交换机实质上是一个**高端口密度的多端口网桥（Multi-port Bridge）**。

1. **工作层次**：
   - 工作在 **数据链路层（第二层，L2）**。
   - 它不仅能感知物理电平，更能**完整解析以太网 MAC 帧头**，提取出源 MAC 地址与目的 MAC 地址。
2. **终结碰撞域（隔离碰撞域）**：
   - **交换机的每一个端口，都是一个独立的、互不干扰的碰撞域**。
   - 端口通常采用全双工通信，内部拥有专用的发送队列与接收队列缓冲区；端口之间通过高带宽的背板交换矩阵（Switch Fabric）实现线速转发。
   - 无论端口 1 和端口 2 的流量有多大，端口 3 上的通信完全不会受到干扰。8 个主机插在 8 端口交换机上，就形成了 **8 个相互隔离的微碰撞域**。
3. **独享带宽**：
   - 如果交换机每个端口标称为 1 Gbps，那么连接在端口 1 上的主机和端口 2 上的主机通信时，可以独占 1 Gbps 的双向传输速率；
   - 其他端口同时对发流量时，只要背板带宽充足，同样各自独享 1 Gbps，不再像集线器那样全员平摊带宽。

### 二、 交换表（MAC 地址表）与自学习机制

交换机能够实现精准点对点转发，依赖于其内部通过 ASIC 芯片维护的高速查找表——**交换表**（工程中常称为 **MAC 地址转发表** 或 **CAM 表**）。

交换表的核心表项只包含三样东西：

```
[ MAC 地址 | 物理端口号 | 老化时间 (TTL) ]
```

最关键的是：**交换表在刚开机时完全是空的，它依靠“自学习（Self-Learning）算法”在无须人工干预的情况下动态建立**。

#### 自学习与转发决策流程（口诀：看源地址学习，看目的地址转发）

假设主机 A（MAC_A）接在端口 1，主机 B（MAC_B）接在端口 2，初始时交换机表为空。

Plaintext

```
主机 A (MAC_A, 端口 1) ----> [ 交换机 ] ----> 主机 B (MAC_B, 端口 2)
```

**步骤 1：看源 MAC 地址做自学习（登记入册）**

- 主机 A 向主机 B 发送一个帧：`[目的: MAC_B | 源: MAC_A]`，从端口 1 进入交换机。
- 交换机首先提取**源 MAC 地址（MAC_A）\**与\**输入端口（端口 1）**：
  - 交换机记录：`MAC_A 位于 端口 1`，并打上当前时间戳。
  - *逻辑*：“虽然我不知道 MAC_B 在哪，但我确信 MAC_A 肯定挂在端口 1 后面。”

**步骤 2：看目的 MAC 地址做转发判决（三种可能分支）**

提取该帧的**目的 MAC 地址（MAC_B）**，查表决定往哪送：

1. **未知单播帧 $\to$ 泛洪（Flooding，盲转）**：
   - 此时表中查不到 `MAC_B`。交换机不能丢包，只能执行**泛洪**操作：**将该帧原样复制转发到除端口 1 之外的所有其他开启的端口**。
   - 网络上其他所有主机收到后，网卡硬件判定目的 MAC 不是自己，静默丢弃；只有主机 B 判定是找自己的，正常接收。
2. **已知单播帧 $\to$ 明确转发（Forwarding）**：
   - 随后，主机 B 针对主机 A 发送回应帧：`[目的: MAC_A | 源: MAC_B]`，从端口 2 进入交换机。
   - 交换机重复步骤 1：记录 `MAC_B 位于 端口 2`。
   - 交换机查表：寻找 `MAC_A`，发现表中已经记录了 `MAC_A -> 端口 1`。
   - **决策**：精准将该帧**直接打入端口 1 发出**，绝不惊动其他任何端口。
3. **同端口帧 $\to$ 过滤（Filtering / 丢弃）**：
   - 如果查表发现，目的 MAC 所在的端口**恰好就是该帧进入的同一个端口**（例如该端口下级联了一个集线器，帧已经在下层完成了本地通信）：交换机直接将该帧丢弃，不向其他任何端口转发。

#### 老化机制（Aging Time）

- 网络中的设备可能会拔掉网线、换插到其他端口，或者更换网卡。
- 交换表中的每一条记录都有一个**老化定时器（通常为 300 秒）**。只要某条记录在 300 秒内没有再次收到该源 MAC 的刷新帧，该表项就会被硬件**自动清除**，防止因拓扑改变而发生路由黑洞。

通过交换机和自学习交换表，以太网成功实现了“微碰撞域隔离”与“硬件线速精确转发”。

## 广播、广播域

### 一、 广播（Broadcast）在交换机网络中的行为

在前面的 MAC 帧结构中提到，**广播帧**的目的 MAC 地址是全 `1`，即 `FF:FF:FF:FF:FF:FF`。

1. **交换机的底层处理机制：永久泛洪**
   - 交换机维护交换表时，只根据**源 MAC** 学习端口映射。因为网络中没有任何合法网卡的物理硬件地址是全 `F`，所以交换表中**永远不可能存在一条指向全 `F` 的端口记录**。
   - 当交换机从某端口收到一个广播帧时，其行为是确定的：**无条件泛洪（Flooding）**，将该帧复制并转发给当前网络内除接收端口之外的所有其他处于连通状态的端口。
2. **广播与“未知单播”泛洪的关键区别**
   - **未知单播泛洪**：是因为交换机暂时没学到目的 MAC，属于临时性的盲转；其他主机网卡比对目的 MAC 发现不是自己后，会在**网卡硬件级别直接丢弃**，不打扰主机 CPU。
   - **广播泛洪**：是协议设计的主动广播；局域网内**所有主机的网卡硬件都会无条件接收并触发中断**，强行把帧内容呈交给操作系统内核（CPU）去解析（例如 ARP、DHCP），消耗全网每台主机的系统资源。

### 二、 广播域（Broadcast Domain）

**广播域**是指：**网络中任何一个节点发送一个广播帧，所有能够接收到该广播帧的节点的集合。**

理解广播域的核心，在于搞清楚物理层、数据链路层和网络层设备对它的控制边界：

#### 1. 三类核心设备的隔离能力对比

| **设备类型**               | **工作层次**     | **能否隔离碰撞域？** | **能否隔离广播域？** | **拓扑影响说明**                                             |
| -------------------------- | ---------------- | -------------------- | -------------------- | ------------------------------------------------------------ |
| **集线器（Hub）**          | 物理层（L1）     | **否**               | **否**               | 既扩大碰撞域，也扩大广播域。所有端口处于同一个碰撞域和同一个广播域。 |
| **以太网交换机（Switch）** | 数据链路层（L2） | **是**               | **否**               | **每个端口都是一个独立的碰撞域；但所有端口默认都处于同一个广播域中。** |
| **路由器（Router）**       | 网络层（L3）     | **是**               | **是**               | **每个接口不仅隔离碰撞域，而且天然终结（阻断）二层广播域。** |

- **以太网交换机不能隔离广播域**：

  如果把 24 台电脑插在一台 24 口交换机上，虽然我们得到了 24 个互不干扰的微碰撞域，但只要其中一台电脑发出一条 ARP 请求广播，**其余 23 台电脑的网卡和 CPU 都会被迫处理这个广播**。

  哪怕用网线将 10 台 24 口交换机级联起来，这 240 台电脑依然捆绑在**同一个巨大的广播域**中。

#### 2. 广播域过大的工程隐患

当一个二层广播域内的节点数量过多（例如超过数百台主机）时，会产生严重的网络病态：

1. **带宽与计算资源被无效侵吞**：ARP 寻址、DHCP 租约续订、各类系统服务发现（如 Windows 网上邻居、mDNS）产生的背景广播流量会持续充斥链路，各主机的 CPU 频繁被中断打断。
2. **安全风险横向扩散**：在同一个广播域内，任何一台主机都可以轻易伪造 ARP 应答欺骗全网（ARP 欺骗与中间人攻击），网络缺乏隔离防护边界。
3. **为“网络回路灾难”埋下伏笔**：由于广播帧在二层交换机中是绝对泛洪的，一旦物理线缆接错形成闭环，就会直接诱发毁灭性的广播风暴。

#### 3. 如何分割广播域？

要打破广播域的无限制扩张，通常有两种技术方案：

- **三层隔离**：使用**路由器**或**三层交换机**，通过 IP 子网进行路由划分（广播帧默认无法跨越三层接口）。
- **二层逻辑隔离**：在交换机上划分 **VLAN（虚拟局域网）**，将一台物理交换机在逻辑上拆分成多个互不相通的二层广播域。
