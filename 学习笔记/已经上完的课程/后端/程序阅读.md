# EL

这类题目的核心考查点有两个：**四大域对象的生命周期（范围大小）** 和 **EL 表达式的就近查找机制** 。  

## 🧭 第一步：死记四大域对象的“地盘大小”

在 Java Web 中，服务器有四个专门用来存取数据的“大口袋”（域对象），它们按照从窄到宽（从小到大）的顺序严格排列 ：  

| **域对象名称**       | **对应的 EL 表达式前缀** | **🚀 口袋的生命周期（地盘范围）**                             |
| -------------------- | ------------------------ | ------------------------------------------------------------ |
| **1. `pageContext`** | **`pageScope`**          | **最小**。数据只在**当前这一个 JSP 页面**内有效，一旦跳走或转发就没了。 |
| **2. `request`**     | **`requestScope`**       | **次小**。数据在**一次请求**内有效。只要是在服务器内部**转发（Forward）**，数据就能带过去。 |
| **3. `session`**     | **`sessionScope`**       | **次大**。数据在**一次会话（浏览器打开到关闭）**内有效。只要你不关浏览器、不点注销，去哪都能拿到 。 |
| **4. `application`** | **`applicationScope`**   | **最大**。数据在**整个 Web 应用**内有效。只要 Tomcat 服务器不关闭，所有用户共享它。 |

## 🧭 第二步：掌握 EL 表达式的两大取值规则

JSP 页面里的 EL 表达式（形如 `${...}`）在取值时，只有以下两种情况：

### 🎯 规则 A：带门牌号的“精准查找”

如果表达式里**写了前缀**（比如 `${requestScope.book}`），这就属于靶向狙击 。  

- 

  **解题方法**：直接去对应的那个域口袋里找这个变量，存的是什么就吐出什么 。**其他口袋里就算有同名的变量，也跟它毫无关系！**  

### 🎯 规则 B：不带门牌号的“无头苍蝇查找”（必考大坑！）

如果表达式里**没有写前缀**（比如直接写 `${book}`），Tomcat 就会启动“就近搜寻法”。

- **解题方法**：按照 **`pageScope` ➡️ `requestScope` ➡️ `sessionScope` ➡️ `applicationScope`** 的顺序，从小到大挨个口袋去摸。
- **终审判决**：**在哪个口袋先摸到了，就直接把那个口袋里的值吐出来，并且立刻停止往后寻找！**

## ✍️ 实战公式推演示例

假设题目在上面塞了一堆数据：

Java

```
<% pageContext.setAttribute("msg", "AAAA"); %>
<% session.setAttribute("msg", "BBBB"); %>
```

1. 如果题目问：`${sessionScope.msg}`
   - **破案思路**：带了前缀 `sessionScope`，精准定位到 session 域。
   - **答案**：`BBBB`
2. 如果题目问：`${msg}`
   - **破案思路**：没带前缀，启动从小到大搜寻法。
   - **搜寻路线**：先看第一关 `pageScope`。一摸，里面有吗？有，值是 `"AAAA"`。
   - **答案**：立刻止步，吐出 `AAAA`！（后面 session 里存的 BBBB 直接被屏蔽掉了）。

# 过滤器

纸考最喜欢考“多个过滤器连在一起（过滤器链 FilterChain）”时的代码输出顺序。我们必须牢记它的底层执行轨迹。

假设我们有两个过滤器（Filter 1、Filter 2）和一个 Servlet，当浏览器发起一次请求时，整个执行流程形成了一个完美的回形针（或回音谷）双向通路：

### 1. 请求阶段（去的时候：正序 ➡️）

1. 请求从浏览器出发，首先撞上 **Filter 1 的前半段代码**。
2. Filter 1 放行后，请求向前撞上 **Filter 2 的前半段代码**。
3. Filter 2 放行后，请求终于到达目的地：**Servlet 的代码执行**。

### 2. 响应阶段（回的时候：逆序 ⬅️）

1. Servlet 执行完毕，开始往外吐响应。
2. 响应原路返回，首先穿过 **Filter 2 的后半段代码**。
3. 穿出后，继续向后穿过 **Filter 1 的后半段代码**。
4. 最终，响应数据才到达客户端浏览器。

> 💡 **终极死记口诀**：**去时 1 ➡️ 2 ➡️ Servlet，回时 Servlet ➡️ 2 ➡️ 1**。

## 🧱 纸考规范：过滤器在代码中怎么分“前半段”和“后半段”？

在过滤器的核心方法 `doFilter` 中，有一行**分水岭代码**，那就是放行语句：**`chain.doFilter(request, response);`**

这行代码就像一道传送门，把过滤器体内的代码一分为二：

Java 

```
public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    
    // 1. 【放行前】—— 这属于“前半段”（请求去的时候执行）
    System.out.println("Filter A 放行前..."); 

    // 🚀 【分水岭】—— 这一句叫“放行”
    // 它的学术含义是：把请求交棒给下一个过滤器（如果没有下一个了，就交给Servlet）
    chain.doFilter(request, response); 

    // 2. 【放行后】—— 这属于“后半段”（Servlet跑完了，响应回的时候执行）
    System.out.println("Filter A 放行后..."); 
}
```

## ✍️ 经典公式推演：人肉跑一次代码

我们把上面的理论组合起来。假设考卷上有两个过滤器，代码分别如下：

- **Filter 1**：放行前打印 `A`，放行后打印 `B`
- **Filter 2**：放行前打印 `C`，放行后打印 `D`
- **Servlet**：内部打印 `Servlet执行`

**控制台的最终打印顺序绝对是：**

> **`A` ➡️ `C` ➡️ `Servlet执行` ➡️ `D` ➡️ `B`**

*仔细看这个结果：`A` 最先出发，却最后才结束（因为它把后面的所有人都包裹在里面了）。这就是学术上经典的**装饰者模式**或者说**多路拦截机制**。*

# 请求包含

## 请求包含（`include`）

既然过滤器链的各种正序、逆序、断流控制已经被你彻底碾压，咱们马不停蹄，立刻去把程序阅读题里隐藏得最深的“冷门刺客”——**请求包含（`include`）** 彻底解决掉。

太原理工大学在 2021 年的真题里，曾经出过这样一道题目，考查的是 `request.getRequestDispatcher("...").include(request, response);`。

很多同学只知道“请求转发（`forward`）”，一看到 `include` 就懵了。

为了让你有绝对的把握，在做真题前，我用一句话帮你拉通它的**学术本质**：

> **`forward`（转发）是“雀巢鸠占”**：A 转发到 B，最终网页上**只有 B** 画的内容，A 自己画的东西会被服务器全部无情扔掉。 **`include`（包含）是“众筹拼单”**：A 包含 B，最终网页上会**同时出现 A 自己画的内容 + B 画的内容**（把 B 的输出结果强行塞进 A 的肚子里，大家其乐融融组合在一起）！

**考场避雷针**：看清题干字眼。问“拦截的**关系映射**元素” ➡️ 选 `filter-mapping`；问“拦截的 **URL 规则/路径** 元素” ➡️ 盯死带有 pattern（规则模式）的 **`url-pattern`**。
