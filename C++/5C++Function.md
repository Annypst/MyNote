### 一、 声明 (Declaration) 与 定义 (Definition)

- **编译器的“死脑筋”**：C++ 编译器自上而下编译代码。若在函数定义之前调用它，编译器会报错不认识。
- **声明**：相当于“菜单”，只告诉编译器函数的名称、参数和返回值类型，不写大括号 `{}`。末尾必须加分号 `;`。
- **定义**：相当于“具体的菜肴”，是函数的具体实现，必须有大括号 `{}` 及其内部的执行代码。
- **原则**：**声明可以有多次，但定义只能有一次**（单一定义规则 ODR）。

### 二、 头文件 (`.h`) 与源文件 (`.cpp`) 的物理分离

- **分工**：
  - **`.h` 头文件**：存放函数的**声明**、结构体声明、类声明，以及内联函数的定义。作为对外的“使用说明书”。
  - **`.cpp` 源文件**：存放函数的具体**定义（实现）**。作为不对外的“核心后厨”。
- **卫哨机制 (`#pragma once`)**：写在头文件第一行，防止该头文件被多次重复 `#include` 导致编译冲突。
- **CMake 多文件构建**：新增 `.cpp` 文件后，必须在 `CMakeLists.txt` 的 `add_executable` 列表中添加对应的 `.cpp` 文件名称，告诉编译器一起参与编译。

### 三、 函数重载 (Overloading) 与底层名字改编

- **概念**：在同一个作用域内，允许函数**同名但参数不同**（参数个数、类型、顺序不同）。仅返回值类型不同不能作为重载依据。
- **底层真相（Name Mangling）**：C++ 编译器在编译时，会根据参数列表偷偷对函数进行“重命名”（例如 `add(int, int)` 会被改写为 `_Z3addii`）。因此，在底层它们依然是完全不同的函数。

### 四、 内联函数 (Inline)

- **痛点**：普通函数调用需要进行**压栈、跳转、弹栈**，如果函数体极小（只有 1-2 行）且被频繁调用，这些开销会严重拖慢性能。
- **解决机制**：在函数前加上 `inline` 关键字。
- **底层行为**：编译器在编译期会将该函数的具体代码直接“复制、粘贴、展开”到每个调用处，省去了函数调用的开销。
- **空间换时间**：由于内联会使生成的可执行文件体积变大，它只适合**代码极短（一般 1-5 行内）、调用频繁、且不含循环和递归**的函数。
- **编译器裁决**：`inline` 只是给编译器的**建议**，如果函数过于复杂，编译器会无情拒绝内联，并将其降级为普通函数调用。

### Example Programs

math_utils.h

```cpp
// math_utils.h
// 这一行是防止头文件被重复引入的“护身符”
#pragma once 

// 声明一个函数（只给菜单，不给具体的菜）
int add(int x, int y);
```

math_utils.cpp

```cpp
// math_utils.cpp
#include "math_utils.h" // 必须引入自己的头文件

// 给出函数的具体定义（后厨做菜）
int add(int x, int y) {
    return x + y;
}
```

main.cpp

```cpp
// main.cpp
#include <iostream>
#include "math_utils.h" // 引入菜单，这样编译器就知道 add 函数存在了

int main() {
    // 编译器在这里看到 add，会去 math_utils.h 里对账，发现对得上，放行！
    int result = add(5, 7);
    std::cout << "5 + 7 = " << result << std::endl;
    return 0;
}
```

CMakeLists.txt

```cmake
# 把 math_utils.cpp 也加入到编译源文件列表中
add_executable(cpp_learn main.cpp math_utils.cpp)
```
